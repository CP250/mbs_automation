Use the mbs_automation skill. Execute `/obsidian-daily`:

This is P's daily safety net — the defense against stress/distraction making him lose the next step. The **Journals plugin already creates** today's daily note; this command **appends a bounded `## Vault Agent` section**, it does not create the note.

1. Read `CLAUDE.md`, `SOUL.md`, `CRITICAL_FACTS.md`.
2. Target file: `daily_notes/tasks/tasks_YYYY-MM-DD.md` (today, US Eastern).
   - **Read the file first.** It already exists (the Journals plugin creates it on open, usually just frontmatter). Claude Code's Edit/Write refuse to modify an existing file that has not been read in this session — so always `Read` the note before appending, or the write fails with a generic error that looks like a permission block but is not.
   - If the Journals plugin genuinely has not created it yet (Read returns not-found), create it minimally with the `journal: tasks` / `journal-date:` frontmatter, then append.
   - Append the `## Vault Agent` section with an Edit that inserts after the frontmatter / existing content. **Leave three blank lines above `## Vault Agent`** so P has space for his own content above the agent's section. Do not overwrite P's own content. If a `## Vault Agent` section already exists from an earlier run today, refresh it in place rather than adding a second one.
   - **Write via the filesystem Edit/Write tools, not the Obsidian MCP.** The scheduled `mbs-daily` agent may run when Obsidian (and therefore the MCP) is down, so the filesystem is the reliable path and the MCP is only a fallback. If an Edit/Write to the daily note fails, do NOT silently switch to the MCP and do NOT guess at the cause: surface the exact error text verbatim and stop, so the real cause (permission mode, sandbox write config, or read-first guard) can be diagnosed. The OS-level directory has been verified writable (`cpreston` owns it; shell append succeeds), so a Claude Code write failure is a Claude Code permission/sandbox-layer issue, not an OS one.
3. Build the report. Append (or refresh) a single `## Vault Agent` section containing, in order, kept to a short and checkable list:
   - **Overdue + due-today tasks** - find unticked `- [ ]` lines with `📅 <YYYY-MM-DD>` due dates at or before today, across all pillars except `trash/` and `_archive/`. **Use filesystem grep (Bash tool with ripgrep/grep), not the Obsidian MCP's `search_vault`.** Obsidian MCP tools are deferred-loaded in headless runs and require a ToolSearch step before invocation; filesystem grep is the reliable path for the unattended morning job. Most urgent first.
   - **Projects missing a next step** — active project notes with no `next_action`. For each, propose one concrete next step. (The headline duty.)
   - **Calendar reconciliation** - pull Google Calendar with `mcp__google-calendar__list-events`, `calendarId='primary'`, `timeMin` set to today's start in ISO 8601 format, and `timeMax` set to the END of day+7 (`<today+7>T23:59:59`). **The window runs through day+7 inclusive.** Corrected 2026-08-13: the prior wording ("7 days out") was read as midnight at the START of day+7, which silently truncated the last day and hid a scheduled event from three consecutive reports. **Expect the calendar tool to be deferred-loaded in the headless run: call `ToolSearch` with `select:mcp__google-calendar__list-events` first, then invoke it.** Corrected 2026-08-13, P-approved: the prior text asserted the opposite in bold, citing a 2026-06-15 verification, and every run from 2026-08-08 onward contradicted it. If `mcp__google-calendar__list-events` itself errors, fall through to `mcp__claude_ai_Google_Calendar__list_events` (same load-then-invoke pattern, different MCP server). **If BOTH calendar MCPs error**, capture the verbatim error string from each in the report (which MCP, what error) and carry forward yesterday's calendar with an explicit "stale, MCP unreachable" flag - never silently degrade. Flag any vault-implied events that are not on the calendar. **Flag only - never create, modify, or respond to calendar events from this command.**
   - **Inbox triage** — new items in `captured/` since last run, each with a proposed destination pillar.
   - **Capture triage** - the `### Triage` subsection (mechanics in step 3c). The heading MUST appear every run, even when there is nothing to propose: the heartbeat's check 9 reads its absence as "the triage step did not run".
   - **Normalization** — up to ~5 convention/`_archive` violations worth fixing.
3b. **Wikilink every vault note mentioned, everywhere in the report.** Any note name that appears in any section (overdue table File column, projects-missing-next-step rows, calendar-vault-implied items, inbox triage, normalization items, the "yesterday's responses" recap) must be a `[[basename]]` wikilink, not a plain backtick-wrapped file path. The vault uses "shortest path" link resolution, so `[[tom_van_riper]]` resolves to `social/people/tom_van_riper.md` from anywhere - no need to spell the full path. Anti-pattern to avoid: `` `social/people/tom_van_riper.md` `` (plain backticks; not clickable in Obsidian). Correct pattern: `[[tom_van_riper]]` (renders as a clickable link in reading view and live preview). This applies even when the path appears as data inside a rename suggestion - prefer `[[old_basename]] → [[new_basename]]` over backticked paths whenever both files have clean snake_case names. For rename items where the source filename has spaces or special chars (broken basename), keep backticks for the source and wikilink the target.

3c. **Capture triage** (project_task_triage phase 1; first live run 2026-08-02). Scope: P's own region of TODAY's note, everything above `## Vault Agent` after the bash carry-forward has run, checkboxes and loose text fragments alike. Skip any `### Work session` block (its heading through the `<!-- /work-session -->` terminator): those are the on-demand work-session command's own top-of-note sections (P's placement decision 2026-08-02), not captures; never classify, route, flag, or count their lines. Propose-only: nothing moves the day it is first seen; a move happens only when a prior day's proposal was answered yes.
   - **Invisible lines (never routed, never flagged, never dropped, never mentioned in the report):** anything credential-shaped: a password-like string, a user/password pair, an account name plus secret, a lone cryptic token. P's standing decision 2026-08-01; do not re-warn about credentials in the note, ever. Also exempt from proposals: lines tagged `#keep` (the standing keep marker; they stay untouched and un-nagged).
   - **Classify every other open line:**
     - Project-scoped (belongs to an existing `project_*` / `goals_*` / `todo_list_*` file): propose routing there.
     - Reference material (book titles, article and product links, research fragments): propose routing to the matching registry, reading list, or reference note.
     - No natural home, single item: propose the exact new destination file; one yes creates it (amnesia-test frontmatter) and routes the item.
     - No natural home, cluster (several items orbiting one unnamed thing): propose an /obsidian-graduate decomposition session, not a stub file.
     - True one-off errand (call, buy, fix, book): stays in the note, no proposal, except staleness below.
     - Noise (duplicate of another line here or of a line already living in a pillar file, clearly dead, resolved-but-never-ticked): propose a drop.
   - **Errand staleness:** read `~/.mbs_automation/triage_first_seen` (tab-separated: `YYYY-MM-DD`, tab, normalized line text; maintained by mbs_daily.sh). An errand first seen more than **14 days** ago (P-set threshold 2026-08-01; change it here and in SETUP.md together) gets one flag: do this week / schedule it / drop. Never flag `#keep` lines.
   - **Execute yesterday's answers first**, before composing today's proposals: read yesterday's `### Triage`. For each proposal marked yes/done: move the item lines out of today's note into the destination, verbatim plus Tasks suffix (`#<pillar> 🆔 <6-char-id>`) when the destination is a project next-action list; create any approved new destination file first. Approved drops: append the lines to `trash/triage_drops_YYYY-MM-DD.md` (create with a one-line provenance header), then remove them from today's note. `skip`: append ` #keep` to the line in today's note; it never gets proposed again. Blank or `defer`: the proposal carries to the next morning unchanged. Report every executed action as one wikilinked line in an **Executed** block at the top of `### Triage`.
   - **Format:** proposals grouped by destination, one `- [ ]` proposal line per group ("route the N items below to [[dest]]"), the affected items as indented sub-bullets, then the standard `status:` / `reply:` fields from step 4. One status answers the whole group; exceptions go in the reply. Cap at ~15 proposal groups per morning; if capped, say what was held back.
   - **Guardrails (binding):** never delete (drops go to `trash/`); prior days' `## Vault Agent` sections are read-only; lines move verbatim, suffix only; errands are never moved, only age-flagged; nothing moves without a prior-day yes; every executed action is reported same-morning.

3d. **Archived-comment sweep** (added 2026-08-01; P: written decisions must not need a second manual handoff). The ambient consumer for comments P leaves on items he ticks and clears (review-prep flags especially). Scope: YESTERDAY's tasks note, `# Archived` section only, lines whose `🔒 [[<date>]]` stamp equals yesterday's date. One-time exclusion: skip any line already present in `~/.mbs_automation/triage_archived_preprocessed_2026-08-01.txt` (a frozen snapshot of the 79 hand-processed lines archived before this feature existed; compare on whitespace-normalized line text). The snapshot only matters while yesterday is 2026-08-01; from the 2026-08-03 morning onward the window has moved past it, and the file is inert history.
   - For each such line, look for P-authored instruction text: a freehand comment appended to the task text (the 🕸️ breadcrumb names the source note, e.g. a review note's Agent prep flag), or non-empty `status:`/`reply:` sub-lines that were ticked and cleared before the in-place reply loop read them.
   - **Clear, low-risk, in-vault instructions execute this run**, reported in the `### Triage` Executed block with the comment quoted and the source wikilinked: status flips ("park" = `status: on_hold` plus a `trigger:` when P names one), defer, move a line to a named note, create a named note, drop to `trash/`. P's written comment on his own ticked item IS his decision (the annotated-checklist rule); this is the one standing carve-out from the propose-only default, P-authorized 2026-08-01.
   - Anything ambiguous, identity-adjacent, outward-facing (email, calendar, anything leaving the vault), or an archive move without the literal word from P: surface as a proposal instead, quoting the comment verbatim.
   - Each archived line is eligible exactly once by construction (the 🔒-equals-yesterday window); no state file needed.

4. Each suggestion gets inline reply fields so P can respond in the note:
   ```
   - [ ] <suggestion> - proposed: <action>
       status:        (done | skip | defer)
       reply:
   ```

   **CRITICAL: the checkbox MUST be at the START of the line.** Do NOT wrap suggestions in a numbered list. The bad pattern `1. - [ ] <suggestion>` is INVALID markdown for an Obsidian checkbox: CommonMark parses `1. - [ ]` as "numbered list item with inline content `- [ ]`", not as a clickable checkbox, so the result renders as literal `[ ]` brackets that P cannot click. This regression occurred from 2026-06-09 to 2026-06-12 in the Normalization section and broke the daily-tasks workflow. If the section needs ordering, use bare `- [ ]` bullets and let the natural list order speak; never combine `N. ` numbering with `- [ ]` on the same line. Sub-items belonging to a suggestion (the `status:` / `reply:` lines, or additional context) get indented under the bullet, no other change.
5. On the next run, read yesterday's `## Vault Agent` section: learn what P did / skipped / deferred, and don't re-suggest things marked `skip`. Persist recurring skips to `CLAUDE.md`'s notes or a `vault_agent/decisions.md` if one exists.
6. **Hard boundaries:** never permanently delete anything; never auto-archive (archiving signals "completed work P wants to keep" and is P's call). Disposal of junk / true duplicates / accidents is via **move to `trash/` at the vault root, no permission needed** (recorded 2026-06-14 in vault `CLAUDE.md` Disposal section). If about to ask "can I delete this?", the answer is: just move it to `trash/` and continue. Moves between active folders (re-organization, not disposal) still require P approval.
7. Append to the operation log: `**HH:MM** — daily | report appended (N overdue, M missing-next-step, T triage proposals, E triage moves executed)`.

This command IS the logic the scheduled `mbs-daily` agent runs each morning. Run it manually anytime to test or refresh.
